## 1. 项目背景与目标

### 1.1 背景
大量在用的业务 App（自助收银、WMS、ERP、门店收银、自建 Web 表单、老旧行业软件）**没有集成摄像头扫码能力**，只接受键盘输入。一线人员只能额外配一把硬件扫描枪，成本高、携带不便、设备管理麻烦。

### 1.2 产品定位
应用名称：**悬浮虚拟扫描枪**（原生 Android App）。

把手机变成一把"**虚拟扫描枪**"：不改造、不侵入目标 App，通过悬浮窗在其他 App 上层取景扫码，把识别结果以**键盘输入**的方式送进当前焦点输入框，并支持硬件扫描枪常见的回车、前后缀等配置。

一句话：**目标 App 以为自己在被人手打字，其实是手机摄像头在扫码。**

### 1.3 目标（可量化）
| 编号 | 目标 | 指标 |
|---|---|---|
| G1 | 识别速度 | 对准条码到内容注入完成 < 400ms（正常光照、常见 1D 码） |
| G2 | 易用性 | 从点击悬浮球到可扫码 < 1s；扫码全程无需切换 App |
| G3 | 兼容性 | Android 8.0–15；覆盖小米/华为/OPPO/vivo/荣耀主流 ROM |
| G4 | 扫描枪配置覆盖 | 前缀、后缀、回车、字符间隔、重复码过滤、连续扫描、注入方式切换 100% 覆盖 |
| G5 | 隐私 | 默认零网络请求、无第三方统计、数据仅存本地 |

### 1.4 目标应用：思迅自助收银（已实测）

**关键事实（在测试机上用 adb 核实，2026-11-04）**

| 项目 | 实测结果 | 影响 |
|---|---|---|
| 包名 / 版本 | `com.sixun.ssposult` v2.5.3（versionCode 26052103） | 可作为适配白名单的精确标识 |
| SDK | minSdk 21 / targetSdk 29 | 跑在兼容模式下，无障碍节点结构与新系统 App 不同 |
| 输入框 | **整个界面没有 EditText**；`dumpsys input_method` 显示 `mServedInputConnection=null` | 无障碍"赋值"（ACTION_SET_TEXT）**无处可写**；输入法 commitText 会直接丢字 |
| 扫码接口 | `dumpsys package` 中**没有任何条码广播接收器**（只有打印服务与开机接收器） | 无法用"发广播"这种最省事的集成方式 |
| 实际收码方式 | 监听原始按键事件（等价硬件键盘 / 串口转键盘的扫描枪） | **必须在输入事件层注入，且必须是真实 KeyEvent** |
| 测试机 | Xiaomi 24031PN0DC / Android 16，已装 Shizuku 13.5.4 且服务以 shell 运行 | 具备免 root 的 shell 注入条件 |

**由此确定的注入架构（V0.4 核心变更）**

```
悬浮窗扫码 → 得到字符串 → 通道选择
                          ├─ 通道 A：无障碍（ACTION_SET_TEXT）→ 仅对"有输入框"的普通 App 有效
                          └─ 通道 B：shell 注入（Shizuku）→ input text + input keyevent 66
                                                      ↑ 思迅自助收银只能走这条
```

**为什么不能只做无障碍**：思迅没有输入框，无障碍服务找不到可编辑节点，任何"赋值/粘贴"都落空。这也是现有 PC 工具在 README 里记录过的同一个坑（`mServedInputConnection=null` 时必须退回 `input text`）。

**通道 B 的代价**：需要手机上有 Shizuku（或等价的无线调试通道）并授予权限；重启手机后 Shizuku 需重新启动。这是本产品唯一的"重门槛"，必须做进新手引导。

**配置指令串场景**：思迅的服务器参数通过扫描如下格式的二维码配置，本 App 需保证这类字符串**逐字符原样送达**（含 `[` `]` `.` 等符号），不做任何转义、截断或编码转换：

```
[]setting[]selfpos[]192.168.10.100[]20100[]0001[]11[]
```

| 术语 | 说明 |
|---|---|

## 3. 用户与场景

### 3.1 角色
- **操作员**（本期为自助收银收银员；后续可扩展至仓库、门店、巡检、快递）：单手操作，戴手套，环境嘈杂，追求"扫一下就走"。
- **配置管理员**（主管/IT）：为不同业务系统准备不同配置档，导出后分发给操作员手机。

### 3.2 典型场景

**S0 首次配置服务器参数（本项目的起点需求）**
思迅自助收银绑定服务器需要"扫描"一张内容为 `[]setting[]selfpos[]192.168.10.100[]20100[]0001[]11[]` 的二维码。手头没有硬件扫描枪，于是：本 App 扫这张码 → 通过通道 B 把字符串原样注入 + 回车 → 思迅解析并保存配置。配置成功后该串进入"常用指令"，以后换机器可一键重发，不必再找二维码。

**S1 单次录入（最高频）**
打开业务 App → 点进输入框 → 点悬浮球展开取景窗并扫码 → 内容填入 + 自动回车 → 悬浮窗自动收起 → 业务 App 完成一次提交。

**S2 连续盘点**
连续扫 20 个条码，每个之间以换行分隔，全部追加进同一个多行输入框；重复扫到同一个码自动忽略。

**S3 自助收银过机（本期主场景，思迅自助收银）**
收银员点悬浮球 → 对准商品条码 → 条码填入收银界面的条码框并自动回车 → 完成一次商品录入 → 悬浮窗自动收起 → 立即扫下一件。要求悬浮窗收起后不遮挡价格、数量、合计区域，且整个过机动作不超过 1.5 秒。

**S4 分屏 / 大屏**
平板或分屏状态下，目标 App 占上半屏，悬浮窗吸附在下半屏固定区域，互不遮挡。

**S5 注入失败兜底**
目标输入框是自绘控件或只读，注入失败 → 自动写入剪贴板 + Toast 提示"已复制，请长按粘贴"。

**S6 配置切换**
同一台收银机上还装着另一个盘点 App，两者对回车的要求不同，通知栏一键切换配置档，无需进设置页。

## 4. 产品范围

### 4.1 本期范围内
Android 原生 App、悬浮窗扫码、**双通道注入（无障碍 + Shizuku shell）**、剪贴板兜底、配置档管理、常用指令、扫码历史、权限与 Shizuku 引导、离线可用、**思迅自助收银适配与验证**。

### 4.2 明确不做
| 不做项 | 原因 |
|---|---|
| **多字段 Tab 拆分** | **本期取消**（原 V0.2 列为 P0）。目标场景确认后，思迅自助收银的条码录入只需单值 + 回车，无多框跳格需求；该功能依赖目标 App 的焦点顺序，投入产出比低。设计备忘保留在附录 A，后续有真实需求再启动 |
| iOS 版本 | iOS 无全局悬浮窗、无跨 App 文本注入通道，键盘扩展不允许开摄像头，技术上不可行 |
| PC 端 / 蓝牙 HID 模式 | 可作为 V2 方向（手机当 PC 扫描枪），本期不做 |
| OCR 文字识别 / 拍照识别 | 非核心，V2 再评估 |
| NFC / RFID | 与"摄像头扫码"定位不符 |
| 后台静默常驻扫码 | 隐私风险 + 耗电，且违背"用户主动触发"原则 |
| 云端账号 / 云同步 | 本期纯本地，降低合规与运维成本 |

### 4.3 可选（V1.x，视进度）
蓝牙扫描枪输入转发、扫码结果规则引擎（正则校验/字符替换）、多语言（中/英）、横屏专用布局。

### 5.3 输入注入（FR-IN，核心模块）

**双通道架构**（V0.4 起）：目标应用决定通道，思迅自助收银只能走通道 B。

| 通道 | 技术实现 | 适用对象 | 前提条件 | 速度 |
|---|---|---|---|---|
| **A 无障碍** | ACTION_SET_TEXT / dispatchKeyEvent 逐字符 | 有标准输入框的原生 App、WebView 表单 | 开启无障碍服务 | 快 |
| **B Shell 注入** | Shizuku 执行 `input text` / `input keyevent 66` | **思迅自助收银**、所有"无 EditText、只收按键事件"的 POS | 手机已装 Shizuku 且服务运行、本 App 已获授权 | 中（一次进程调用 60–150ms） |
| C 剪贴板兜底 | 写入剪贴板 + 提示手动粘贴 | 两条通道都失败时 | 无 | 需人工 |

**降级原则**：Shizuku 是可选增强，不是必需依赖。通道 B 不可用（未安装 / 服务未启动 / 未授权）时，App 必须正常启动、正常扫码，自动退到通道 A，再退到通道 C，并在悬浮球上以颜色区分当前通道。对思迅这类无输入框的应用，退到 A 必然失败，此时要明确提示"需启用增强通道（Shizuku）"，而不是让用户看到"发了没反应"。

### 6.1 商店上架合规（因分发渠道确定为商店，此节为硬性要求）

无障碍（AccessibilityService）是商店审核的高敏感权限，尤其 Google Play 明确限制将其用于"自动化操作其他应用"。上架成败取决于说明是否清晰、功能是否可被审核员复现。

| 要求 | 说明 |
|---|---|
| 权限声明与用途 | 每项敏感权限（相机、悬浮窗、无障碍、前台服务）在隐私政策与商店后台"权限声明"中逐条对应到具体功能，避免笼统表述 |
| 无障碍用途定性 | 统一表述为"**辅助键盘输入**（替代外接扫描枪），仅在用户主动触发的扫码动作后向当前输入框写入文本"，不出现"自动化操作""模拟点击其他应用"等表述 |
| 审核可复现 | 提供一个内置的"演示模式"（App 内自带一个测试输入框），审核员无需第三方 App 即可走通全流程 |
| 首发范围 | 建议先上国内主流商店（华为/小米/OPPO/vivo/应用宝）跑通流程，Google Play 作为第二阶段单独评估 |
| 上架材料 | 隐私政策 URL、权限使用说明文档、功能演示录屏、软件著作权（国内商店通常需要） |
| 敏感权限开关 | 无障碍与悬浮窗必须由用户手动开启并可在应用内一键关闭，不得默认开启或诱导开启 |
| Shizuku 依赖声明 | 通道 B 依赖用户自行安装的第三方提权工具 Shizuku，商店描述中须明示"可选增强依赖"，并保证未安装时 App 主体功能可解释、可演示（否则审核员无法复现） |

## 9. 验收标准（关键项）

1. **配置指令（第一验收项）**：扫描含 `[]setting[]selfpos[]192.168.10.100[]20100[]0001[]11[]` 的二维码，思迅自助收银成功解析并保存服务器配置（IP `192.168.10.100`、端口 `20100`）。
2. **商品过机**：在思迅条码录入界面注入条码并自动回车，完成一次商品录入；连续过机 20 件无失败、无串位。
3. **字符串零损伤**：注入前后逐字符比对，`[ ] . : _` 等符号无丢失、无转义残留、无多余空格。
4. 配置"前缀 PDA- / 后缀 \r\n"，扫码后内容为 `PDA-6901234567892\r\n`，且触发一次提交。
5. 同一码连续对准 5 秒，只注入 1 次。
6. 连续扫描模式下扫 5 个不同码，结果按换行累加在同一个输入框内。
7. 通道 A 在普通 App（如浏览器输入框）中可用；通道 B 不可用时给出明确提示而非静默失败。
8. 关闭 Shizuku 或重启手机后，首页与悬浮球明确提示"通道 B 不可用"，并提供一键重连指引。
9. 分屏模式下悬浮窗不越界、不遮挡目标输入框。
10. 目标 App 置于后台 30 分钟后，切回仍能直接扫码注入（服务未被杀）。
11. 飞行模式下全功能可用（Shizuku 通道不依赖网络）。
12. 应用内置"演示模式"，在无第三方 App 的干净设备上可完整走通"扫码 → 注入 → 回车"全流程（商店审核用）。
13. "注入自检"能正确报告通道 A、B 在当前界面的有效性与耗时。

## 附录 A：暂缓功能备忘——多字段 Tab 拆分

> 状态：**本期不做**（V0.3 移出范围）。此处仅保留设计结论，避免后续重启时重复调研。

**原设想场景**：一条码内含多段信息（物料号 + 批号 + 数量），业务 App 有多个输入框，靠 Tab 跳格逐段填入。

**当时的设计结论**：
- 拆分规则三种：分隔符（`A1001|20260101|50`）、固定长度（`6-8-3`）、正则捕获组。
- 执行链：注入第 1 段 → 发 Tab → 校验焦点是否变化 → 注入第 2 段，以此类推。
- 关键风险：焦点跳转不可控，目标 App 的 Tab 顺序与视觉顺序可能不一致；必须靠"演练模式"预演，并在焦点未跳转时立即中止。

**取消原因**：目标场景（思迅自助收银）的条码录入是单值 + 回车，不存在多框跳格需求；该功能成本高、通用性差。

**重启条件**：出现明确的多字段表单场景，且能拿到真实目标 App 做焦点顺序验证。

## 附录 B：测试环境备忘——思迅界面无法投屏（FLAG_SECURE）

> 状态：已知限制，非缺陷。

**现象**：QtScrcpy / scrcpy 投屏时，思迅自助收银显示为纯黑，手机上正常。

**原因**：目标窗口设置了 `FLAG_SECURE`。实测证据：

```
dumpsys window windows | grep sixun
  fl=KEEP_SCREEN_ON LAYOUT_IN_SCREEN FULLSCREEN SECURE ...
```

`SECURE` 会让 SurfaceFlinger 对所有截屏通道返回黑帧，因此 scrcpy、`adb exec-out screencap`、系统录屏、投屏全部失效（实测截图平均亮度 0.0），与投屏软件版本无关。

**应对（按代价排序）**：

| 方式 | 做法 | 代价 |
|---|---|---|
| 直接用真机屏幕 | 手机放桌上，电脑只发注入命令 | 无，推荐 |
| 读视图树代替看图 | `adb shell uiautomator dump` 读取界面文本，判断是否出现"配置成功"等字样（FLAG_SECURE 只挡像素，不挡视图树） | 无画面，但验证注入结果更准 |
| 改包 | apktool 反编译去掉 `setFlags(FLAG_SECURE)`，重签重装 | 仅限本地测试机，签名变化导致重装与数据清空；不得外传 |
| Root + LSPosed | 装"去除 FLAG_SECURE"模块 | 需 root，测试机未 root |

**产品层面的含义**：本 App 永远不尝试抓取目标应用画面，悬浮窗只回显"自己扫到的内容"和"注入结果"，这在技术上也根本抓不到。

### E.2 关键设计决策

**1. 降级不能造成重复注入**

无障碍 `ACTION_SET_TEXT` 成功后若回车失败，若返回"整体失败"，路由会继续走 Shizuku 把同一段内容再发一遍。故引入独立状态 `OK_NO_ENTER`：文本已写入、回车未发，路由**不再降级**，只提示"内容已写入，但回车未能发送"。这是本轮最容易出错的地方，已作为回归重点。

**2. 弹窗检测取保守策略**

初版按"存在第二个应用窗口即视为被遮挡"，实测把状态栏、导航栏、输入法全部误判。改为：只把**位于焦点窗口之上、且含有「确定/知道了/OK」这类关闭按钮**的窗口判定为模态框。宁可漏判（此时按无弹窗继续），也不误拦，避免正常扫码被无谓阻止。

**3. 常用指令的发送入口必须在悬浮面板**

注入目标是"当前焦点窗口"。若在主界面点发送，焦点在本应用，内容会打到自己身上。因此 `SnippetsActivity` 只负责维护清单（点按 = 复制），真正的一键发送放在悬浮面板的「指令」按钮，弹窗同样以 `TYPE_APPLICATION_OVERLAY` 显示，关闭后延迟 250ms 再发，等焦点回到目标 App。

**4. 历史不提供"重发"按钮**

同上原因，在本应用内重发只会打进自己。历史提供复制，重发请用常用指令或在目标 App 内粘贴。

**5. Android 8–9 的无障碍回车限制**

`ACTION_IME_ENTER` 自 API 30 才有。低版本上：多行输入框把 `\n` 拼进文本收尾；单行输入框只能返回 `OK_NO_ENTER`。这是系统能力边界，不通过 hack 绕过。

回归中发现并修复的两个缺陷：

1. **单帧误读直接注入**。同一张静止条码 7 秒内被解出 6 个不同的 EAN-13 值（校验位碰巧合法），原实现逐帧注入，11 次里有 6 次是错码。新增 `ScanGuard`：注入成功后整体上锁、连续 700 ms 无识别结果才解锁、解锁后 1.2 秒内不接受内容不同的新码。真机上条码静止 15 秒零触发，日志中可见被丢弃的 3 个可疑值。
2. **并发注入字符交错**。Shizuku 单次注入约 280 ms，分析帧每 100 ms 到达，多个 `input text` 同时往一个输入框打字，真机出现过 `349012P60D39A269EN86D3472` 这类交错串。注入已收敛到单线程执行器。
3. **累计投票仍放过错值**。确认器最初是"同值 1 秒窗口内累计 2 票放行"，真机上正确码与错码 `7904869343434` 交替出现，错值凑够 2 票被当成新商品注入；该错值 EAN-13 校验位合法，加校验位也拦不住。改为**连续 3 帧一致**才放行（中途插入任何不同值或空帧即重新计数）。离线回放六种帧流全部符合预期。
4. **无障碍误判"目标没有输入框"**。`findTarget()` 只看 `getRootInActiveWindow()`，软键盘展开时部分 ROM 把活跃窗口判给输入法窗口，导致误判无输入框而降级到 shell；而 shell 的按键注入会被中文输入法做全角标点转换并延迟提交，真机出现过 `PDA-6901236347102-ENDPDA69236347－102END`（含全角 `－`）。定位改为两级：活跃窗口失败后遍历所有 `TYPE_APPLICATION` 窗口，先看带输入焦点的。修后连测 5 次均为 `order=[1,2,3]` + `a11y -> 0`，内容稳定、回车精确 +1。
5. **抖动导致同一次呈现被切成多次**。解锁门槛是"连续 700 ms 无识别结果"，而手持包装对焦抖动时，实测静默时长恰好落在 703 / 708 / 723 / 729 ms，每次刚过门槛，于是同一个条码在 12 秒内被录入 4 次（`enter` 6→9）。判据改为量"标签实际离开画面多久"：同一个码重新录入要求离开时长 ≥ `max(1.2 s, 去重窗口)`，手抖级别的回来一律按同一次呈现丢弃。用真机这段 4 连录时间线回放，注入次数 4 → 1，日志可见 `UNLOCK gone 720ms` 后紧跟 `REJECT_DUP awayOnly=720ms need=1500`。同时在真机上复测：条码静止 25 秒、40 秒各零事件，`enter` 不变。
6. **无障碍被系统解绑导致静默降级并写坏内容**。HyperOS 会无声解绑无障碍服务（设置里仍显示启用），路由随之降到 Shizuku；而 shell 按键注入落进"有焦点的输入框 + 中文输入法"时只提交半截，真机目标框出现 `PDA-6901236347102-ENDPDA`（末尾 `PDA` 是本次只提交的开头），状态栏却报 `Success`。现在走 Shizuku 且无障碍未连接时，状态栏明确显示 `text may be mangled — accessibility is off`，`VSG-Router` 同步打 `shizuku used while accessibility is disconnected`。已实测：断开 → 降级并告警；重新开启 → 立即回到 `order=[1,2,3]` + `a11y -> 0`。
